三、开发规矩（接手的人必读）
==================================================================
  1. 日志纪律：每轮开发先更新日志再动手；阶段结束把总纲压缩成纯
     大纲，逐轮明细归档到 `X.X.X开发日志-历轮明细.txt`；
     【需要你操作】永远放文件最底部。
  2. 版本控制（硬规矩，★ 1.9.2 更新）：项目已用 git（任务 1）。
     改代码前不再手抄 .bak —— 改成"动手前先确认工作区干净
     （`git status`），改完跑绿了立刻 commit"。真想留退路就先 commit
     一次当前状态，用 git 回退，别再堆一堆 .bak 文件。
     （1.9.2 任务 2 已把历史遗留的 70 个 .bak 全部丢进回收站。）
  3. 回归三连：改完必须跑 py_compile + 专项测试 + _test_a190.py，
     全绿才算完；数字必须实测，不许凭记忆写"大概"。
  4. 离线测试 ≠ 真机验证：offscreen 测试过了不等于真机没问题，
     涉及窗口/DWM/托盘的必须真机过一遍。
  5. 涉及安装新依赖、要密钥、要账号的操作，先问用户，不许自作主张。
  6. 实测数字必须真实：所有 PASS/FAIL 数、耗时、内存占用，以实际
     运行输出为准。
  7. 沙盒事实：终端会因挂起的 python 进程卡死；python 命令挂住时，
     cmd 内建（copy / echo）往往还能用；任务管理器清进程后恢复。
  8. 编码：日志与代码统一 UTF-8，注意 BOM；中文标点不要转半角。
  9. 模块生命周期是 LAZY：延迟加载，用时才 import；新工具必须带
     TOOL_NAME / TOOL_DESCRIPTION / TOOL_PARAMETERS 三件套。
 10. Qt 大坑清单：setPixmap 同一张图是 no-op，必须 clear 或换
     指针；窗口 flag 改动要在 hide 状态下做；定时器回调里别碰
     已销毁对象。
 11. 记忆纪律：用户让记的才记；回归没跑完不许改别的文件；
     Path("") 的坑（cwd 漂移）要警惕。

  ★ 真凶是 `nativeEvent()`（`pet_animation.py` 原 441/446 行）：
    **每次调用都新建一个 `_MsgHdr(ctypes.Structure)` 类，再对这个新类调
    `ctypes.POINTER(_MsgHdr)`。** 而 CPython 的 `ctypes.POINTER()` 会把结果存进
    **模块级永久字典** `ctypes._pointer_type_cache`，**key 就是这个类、强引用**

        · RSS 15.62 → **127.82 MB**（≈5883 B/次）
        · `_pointer_type_cache` 20 → **20021 条**，`gc.collect()` 之后**仍是 20021**
    而 `nativeEvent` 被调用得很频繁（看门狗每 3 秒重绘一次，每次重绘都产生原生
    消息）→ 每小时十几~几十 MB，与你观察到的"42MB 后缓慢上升"数量级吻合。

  → **修法**：把结构体 `_MsgHdr` 与指针类型 `_MSG_HDR_PTR` 提到**模块级只建一次**，
    `nativeEvent` 里改成 `ctypes.cast(addr, _MSG_HDR_PTR).contents`；
    并对非 Windows 原生消息提前 return（少一次解析）。
  → **验证**：20000 次解析后缓存条目 **4 → 4（零增长）**；

二十八、★ 1.9.2 第十九轮 —— 你问"预览不落盘会不会影响重启后加载"（结论 + 决定）
==================================================================
  [R44] **原文**：
       ###压缩后的预览图不落盘，会不会影响后期加载？重启后是否可见？如果有影响，
          就还是落盘到data文件缓存，聊天界面找不到源路径文件就显示"图片被清理了"占位。

  ★ 直接回答（**读码**得出的确定结论）：**不影响重启后的加载，重启后照样可见。**
    原因：聊天记录里存的是**原图的绝对路径**（正文里写 `<img src="file:///…">` 指向原图），
    **根本不是**预览图。预览是**渲染时**当场从原图算出来的派生数据：
      · `chat_widget.py:1109 _render_inline_image_html()`、`:1994` 那段
        —— 用 PIL 只读图片头拿宽高（很便宜），算出 260px 的显示尺寸，
          然后发出 `<img src="file:///原图">`。
      · 所以"预览"这件事**本来就不产生任何文件**，它只决定"按多大解码/显示"。
    重启后：同一段代码 + 同一个原图路径 → 生成一模一样的预览。**什么都不会丢。**

  ★ "不落盘"的**唯一**代价：原图**被删/被移动**时，预览也算不出来（它是从原图算的）。
    而这种情况**现在已经做了占位**（读码确认，三种都有）：
      · `file://` 图缺失   → `[图片不可用: 名字]`（`:1133`）
      · `append_image` 缺文件 → `[图片不存在: 名字]`（`:2012`）
      · 文件卡片缺失       → `[文件已不在]`（`:1061`）
    → 你要的"找不到源路径就显示占位"**已经存在**了，我只需要把文案统一成你说的
      「**图片被清理了**」，并把原路径一起显示出来（方便你找/清理）。
