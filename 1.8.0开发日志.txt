二、核心机制
────────────────────────────────────────────────────────────────
1. 形象线程 PetManager：单线程队列串行处理 切角色/切行为/切 GIF；
   接收 LLM 思考流（reasoning_content），思考结束按 {"gif":"名字"} 协议切 GIF。
2. 启动默认 GIF「只播放一遍」：渲染端按帧号回绕判断播完 → gif_once_finished
   → 形象线程立即衔接待机轮播（12 秒兜底定时器）。
3. 一个角色一个窗口：topics 表按 character 归属，每角色一个 active 话题（连续上下文）。
   「＋ 开启新话题」直接开；「📝 总结旧话题」总结→归档→开新话题并继承总结；
   上下文满自动总结续接（不阻断输入，消息暂存后补发）。
4. 侧栏 = 聊天窗口**左侧外面的独立窗口**（聊天窗口尺寸/内容完全不受影响）；
   书签 = 一段对话一条总结，左键跳转（按隐形标记 ⟦T<id>⟧ 搜索），右键删除（db + 界面）。
5. 图片：用户上传走右侧；桌宠（LLM/tool send）走左侧 + 桌宠头像；
   相对路径必须 resolve 成绝对路径才能 as_uri()。
6. 工具沙箱：用户电脑全盘只读，只有 data/桌宠私有data 可写。
7. 角色设置全部存 data/桌宠形象/<角色>/settings.json
   （persona_prompt / scale / reply_style / emoji_level / behavior_gifs /
    startup_gif / idle_gifs / idle_switch_rule / model / avatar / icon）。
8. TTS 内存策略：GENIE 模型默认**不启动预加载**，空闲 15 分钟自动释放（省 ~4.5GB）。

【检查结论：数据流有 3 处断链/污染】
① monitoring_events → 长期记忆 断链：DB 里 get_unprocessed_events /
   mark_memory_processed 两个接口从未被调用，监控事件永远到不了长期记忆。
② chat_records → 长期记忆 断链：chat.get_unprocessed / mark_processed
   同样无人调用；聊天记忆只有 LLM 主动调工具才进库，被动链路不存在。
③ 两条污染环：
   a) 旧 LLM1 定时总结(_flush_batch_summarize)把总结经 add_memories_batch
      写回 raw_events（cleaned=0）→ 被 Pipeline 当原始数据再清洗 → 总结→再总结；
   b) 增强输入监控（剪贴板/窗口/进程）根本不落库，Pipeline 拿不到这批数据，
      只有旧 LLM1 路径在消费它。
④ 屏幕视觉总结(_process_screen_image)也写回 raw_events，同③a 污染。

【改动】

     _pending_memory_ids 在途去重。

PTRTS1.7.2_DSH (hotfix)  —— 2026-09-15 18:50
1，从源头关闭 deepseek 推理模型 thinking
2，兜底判断逻辑（独立 YES/NO 正则）
3，强化 detect prompt 禁止思考

────────────────────────────────────────────────────────────────
【症状：1.7.1 修复后仍判 "LLM 不可用"】
prts_20260915_1845*.log 每轮仍出现：
  [LTM] 检测返回异常: 'WE NEED TO DETERMINE IF THE CONVERSATION...'
  [LTM] 检测返回异常: '我们需要判断这段对话是否包含值得长期记忆的信息。规则层...'
注意：这次错误**不再是空字符串**，而是 reasoning_content 的截断思考过程。
64 token 不够推理模型思考完，content 全空 → 兜底到 reasoning → 失败

【根因】
deepseek-flash 默认启用 thinking/reasoning_content，64 token 思考到一半
就被截断。_detect_memorable() 读不到 YES/NO 结论。
我之前那段判断逻辑 "if 'YES' in content and 'NO' in content" 直接返 None
（因为 reasoning 里反复说"输出 YES 或 NO"），所以每次都是 None → 失败。

【三层修复】
A. 从源头关闭 thinking（治本）：
   · _get_llm() 检测 host 含 deepseek 且 model 含 flash/reasoner/r1 → _disable_thinking=True
   · 新增 _chat() helper，对 _disable_thinking=True 的调用
     透传 extra_body={"thinking":{"type":"disabled"}}
   · 普通模型不传 extra_body（兼容其他 OpenAI 兼容协议）

B. 兜底判断逻辑（治标）：
   · _extract_text() 保留兼容（content 为空时回退 reasoning_content）
   · 正则 (?<![A-Z])(YES|NO)(?![A-Z]) 找**最后一个**独立 YES/NO
     · 兼容 "结论YES"（中文紧贴）、"最后：NO"（标点紧贴）
     · reasoning 里复述规则时出现的 YES/NO 不作为判断（取末尾）

C. 强化 detect prompt：
   · "严格规则：不要思考、不要解释、不要分析。看完对话后，
     最后一行只输出一个单词 YES 或 NO。"

D. 测试矩阵：
   · tools/dev_tests/_test_ltm_171.py   mock 测试 13 项 PASS

PTRTS1.8.8  —— "按道理来说这些监控数据应该会先机械清洗，然后才是 LLM 清洗吗？"

【先回答顺序：你理解得对】
_process_batch 的实际链路就是：
   取数 get_uncleaned(100)
     → _fetch_uncleaned（时间/ID 过滤）
     → _mechanical_clean（机械清洗，纯规则、不花钱）
     → _dedup_events（★ 本次新增：重复合并）
     → _enrich_file_paths（标 [待视觉分析]/[待STT转写]）
     → _llm_summarize_with_retry（LLM 清洗）
     → 写 monitoring_events → 标记 raw cleaned=1 → 喂长期记忆
   机械清洗在前、LLM 在后，设计上是对的。

【但实测：机械清洗一直在空转】
日志里那行 "获取 100 条原始数据 → 机械清洗后保留 100 条" 就是证据。
用真实库跑了一把（tools/dev_tests/_diag_pipeline_layers.py）：

  raw_events 总 1058 条，cleaned=0 也是 1058 条（一条都没清洗过）
  第2层 _fetch_uncleaned：100 → 100（没过滤）
  第3层 机械清洗：     100 → 100   四条规则一条都没命中

  真实 source 分布：process_metadata 44 / window_metadata 39 / system 14
                    / keyboard 2 / clipboard 1
  而规则1 的 source 白名单写的是 ("process", "system")
  → "process_metadata" 根本不在白名单里，规则1 对 88% 的数据永远不生效

【所以这一批数据是「重复度极高的原始数据」直接丢给 LLM】
  归一化后重复：65/100 条
    ×44  [process_metadata] "活动应用类别: browser, ide"
    ×6   [window_metadata]  "切换应用: python.exe | 窗口: python"
    ×5   [system]           "[进程] idea64.exe(1进程, N MB)…"
  既费 token，又让 LLM 把注意力花在 44 条一模一样的话上。

【本次修法（你选的"两个都修"）】
1. 规则1 的 source 白名单改成前缀匹配 ("process","system","window")
   → process / process_metadata / window_metadata / system 全覆盖；
   噪声词改成词边界正则（crash|gpu-process|utility|renderer|
   network-service|video-capture），
   避免窗口标题里出现 "Storage 管理" / "audio track" 就被误杀。
2. 新增 _dedup_events：同一批里「同 source + 同归一化内容」合并成一条。
   归一化 = 去掉数字与 "持续 Ns"（"[进程] idea64.exe(2749MB)" 与
   "(2097MB)" 视为同一种状态）。
   合并策略刻意**保留首次出现的位置与时间戳**，把末次时间与次数写进正文：
     "活动应用类别: browser, ide（同批 ×44，至 2026-09-15 21:10:00）"
   —— 比直接丢弃更有用：LLM 既知道"这段时间一直是这个状态"，
      又保住了时间跨度，数据也不丢。
   顺序：机械清洗 → 重复合并 → LLM（合并日志会写明省了多少条）。

【真实数据上的效果（实测，不是估算）】
   取数 100 → 机械清洗 100 → 重复合并 35
   → 送进 LLM 的数据量减少 65%
   （机械清洗这次仍滤掉 0 条 —— 你的数据里本来就没有浏览器子进程噪声；
     白名单修复是让规则"能生效"，不是硬凑数字。）

PTRTS1.8.9  —— "感觉永远都总结完" → 大力清洗

【先说结论：上一轮的 1.8.7/1.8.8 其实生效了，而且真清完了】
看 logs/prts_20260915_213404.log 全程 21:35→21:52，再查库：
   raw_events 1027 条：cleaned=0 只剩 55 条，cleaned=1 有 972 条
   monitoring_events 从 4 条涨到 70 条，且全部已喂长期记忆
   重复合并也确实在工作：100→35 / 100→22 / 100→20 / …（每批省 65%~82%）
所以积压不是没清，是**清得慢且看不出进度**。

【你感觉"永远清不完"的两个真实原因】
1. 单批硬编码 100 条，1058 条积压要跑 11+ 批；而且每批之间隔 60s
   （主循环 wait(timeout=60)），于是 21:35→21:48 连续 13 分钟
   每分钟都在调一次 LLM —— 看着就像永远不会结束。
2. 心跳里的"积压=100"是**假象**：它用的是
   len(get_uncleaned(limit=100))，被 limit 截断了，永远显示 100。
   实际上当时库里还有 900 多条没清。数字不动，当然像卡死了。

【按你的要求加的「大力清洗」】
规则：积压 > bulk_threshold(500) → 本批直接取 bulk_batch_size(500) 条。
顺序仍是你说的那样：先机械清洗 → 重复合并 → 再 LLM。

具体改动：
· src/utils/config.py  PipelineConfig 新增
    bulk_threshold   = 500   积压超过这个数就进大力模式
    bulk_batch_size  = 500   大力模式单批取多少条原始数据
    bulk_max_tokens  = 4000  大力模式 LLM 输出上限
  （现有 config.json 里还没有这三个字段，会先用 dataclass 默认值，
    下次保存配置时自动写进去；想调大小改 config.json 即可。）
· src/core/database.py  新增 count_uncleaned()：待清洗**真实总数**
  （不再被 limit 截断）。
· src/core/data_pipeline.py
  - 主循环用 count_uncleaned() 判定积压；>500 → bulk，单批 500；
    100~500 → 仍是常规单批 100（行为和以前一致）。
  - _process_batch(batch_size) 接受单批条数，并把它传给取数。
  - 心跳/启动日志显示真实积压与当前单批大小。
  - LLM 的 max_tokens 跟着输入条数放大
    （max(2000, min(4000, 1200 + 输入条数×12))），
    避免 500 条合并后约 175 条进 prompt 时 JSON 被截断
    （日志里 21:39:45 就出现过一次 "JSON 解析失败 (第1次)"）。

【顺带根治一个会让流程永久卡死的隐患】
   _fetch_uncleaned 原来的窗口写死 id_diff<=100 / 60s。
   单批改成 500 后，取到的 500 条里最旧的那些 id_diff 会 >100 →
   被剔出本批，**而且不会被标记 cleaned** → 下一批又排在最前面被剔
   → 永远卡住。这正是"永远清不完"可能演变成死锁的地方。
   现在：窗口随 limit 缩放（id_window=max(100,limit)，
   time_window=60×(limit/100)）；并且加了「保底推进」——
   万一真有行落在窗口外，也**不许丢**，只记一条 warning 并全部保留。
   宁可多送几条给 LLM，也不能让流程卡死。

【HIGH：用户画像提取整条链路是死的】
user_profile.py:177 `result = self._llm.summarize(prompt)`
—— SummarizerClient.summarize() 返回的是 **list[str]**（"- xxx" 记忆条目），
